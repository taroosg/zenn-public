## 状況

プロジェクト構成：

- フレームワーク: Next.js
- バックエンド: Convex
- ワークフロー: AI駆動の issue→レビュー→PR フロー

使用AI：Claude Code（Fable（メイン），Opus（サブ），Sonnet（サブ））

開発中，最も早くリミットに達するのは「週次 · Fable」．次いで「週間 · 全モデル」．自分の環境では日曜21時にリセットとなるため，開発が多い週は金曜にFableが上限に達していた．

## 使用状況

- コスト構成: cache read 60 % / write 26 % / 出力 13 %
- Fable 5メイン=コスト 61 %，メイン平均コンテキスト 21万，複数 issue 連続セッションは25〜54万
- Fable 5がサブとして 2,467 msg 稼働，モデル未指定で Agent 起動すると Fable で起動してコストかかる
- セッション内再Read率 72 %・grep出力 20 M 文字・git diff 14 M 文字・MEMORY.md常駐 5.9 k/セッション（マージ済み PR 行が蓄積中）

方策：連続セッションはなくす，サブエージェント起動時は必ずモデル指定する，異常時以外の出力は全部出さずにまとめる，MEMORY.md は適宜整理する．品質検証に使うトークンは削らず，重複・冗長・生出力だけを削る方針とした．

計測方法: Claude Code のローカルセッションログ（JSONL）を全数集計し，モデル別・役割別・キャッシュ別トークンをAPI公表単価で換算．

## 総合結果

- コスト（変更1,000行あたりのAPI換算で正規化）: −8%
- モデル出力トークン（同・仕事量あたり): −42%
- 品質シグナル: 劣化なし（レビューすり抜け新規記録0・revert 0）

## 効果があったもの

- サブエージェント起動のモデル明示を必須化：モデル未指定で起動したサブエージェントは親の最高単価モデルを継承する．規約1行で根絶し，該当消費 $259 → $0．未指定起動0件に．
- 実装委任のカスケード化：「難易度を事前分類して上位モデルに委任」をやめ，「常に安いモデル → 失敗時のみ昇格」に変更．上位モデルへの実装委任 49 回 → 0 回，事前分類が上位モデルを過剰使用していたことの実証．issue がいい感じに作成できていれば実装は Sonnet でいい．
- 常駐コンテキストの削減：毎セッション自動ロードされるメモリ索引から消化済みタスク記録を退役（−62 %）．放置すると単調増加する構造だった．
- レビュアー定義の意味保存圧縮：レビュー起動のたびに再注入されるエージェント定義を，基準を緩めずに −24 %．低頻度参照部は別ファイルに分離して状況に応じて参照．

## 効果が部分的だったもの

- コマンド出力の絞り込み規約：（件数は `grep -c`・diff はまず `--stat`）— grep 出力は −23 %/回．git diff は横ばいで定着に差．
- 1 課題 = 1 セッション運用：平均コンテキストは −31 %（54 万→ 38 万トークン）．機能開発ではコンテキスト多めになるため引き続き検証．

## 効果がなかったもの

- 再レビュー周回の読込範囲限定：「不明な場合は全読込にする」フェイルセーフが標準経路で常時発動し，ほぼ非発動．安全設計が削減効果を無効化した．レビューの質が下がるリスクもあるためやらなくてよい．
- テスト/フォーマッタの成功時出力抑制：導入自体は完了したが効果は限定的．事前見積り（全スイート実行前提）に対し，実際の実行の大半は単一ファイル実行で元々出力が小さかった．
- ルール追記による逆効果：改善規定の追記自体が最頻ロードのスキル文書が 1.9 倍（9.4 → 18.1 KB）に肥大した．トークン削減のルールもトークンを消費する．追記の是非というよりは追記による効果との塩梅が重要．

## まとめ

まだ試行錯誤段階．各作業の内容で効果の有無も異なるため，正しい結果を得るためには一定期間開発を進める必要があり今後も監視を継続する．今回の改善で Fable のリミットと週間のリミットが同程度のスピードで推移する状態になった．

- モデルの割り当てミスの根絶は最重要で，テクニックよりも「誰がどのモデルで動いているか」を実測で確認する．
- 委任は事前分類よりカスケード（安いモデル既定 + 失敗時昇格）．
- ルールを足すときはそのルール自体の常駐コストを考慮する．
- 出力・成功ログの削減は品質と衝突しない．検証に使うトークンと重複・冗長を区別して，後者のみ削る．

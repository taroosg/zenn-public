## この記事について

- 目的: アプリケーション開発におけるセキュリティの基本を，チームで共有する．
- 題材: 最近の個人情報流出事例と，FanSourceで実際に行っている対策．
- 扱う範囲: アプリケーションの設計と実装で防げること．
- 扱わない範囲: 組織全体の教育，端末管理，フィッシング訓練，ランサムウェア対策など．

## 1. 最近の流出は「どうやって」起きているか

高度なハッキングを想像しがちだが，公表された事例を読むと，原因は基本的なところにある．3つの型を紹介する．

### 型1: 見えてはいけないものが見える（設定・権限の誤り）

コスモ石油マーケティング「コミっと車検」（2025年6月公表）

- クラウドに保存していたファイルの一部で閲覧制限の設定が誤っており，外部からアクセスできる状態だった．
- 対象は2019年8月〜2025年5月の申込情報．電話番号 約17万6千件，氏名 約3万5千件，車両情報 約11万9千件など．
- ファイルは「推測が難しい URL を全文入力しない限りアクセスできない」状態だった．
- 2023年1月より前はアクセス履歴を取得しておらず，外部から見られたかどうかを確認できていない．

ここから読み取れることは2つある．

- 「URL が推測しにくい」ことは，鍵をかけたことにならない．URL は転送やブラウザ履歴などで漏れる．「誰が見てよいか」を毎回確かめる仕組みが必要である．
- ログがないと「被害がなかった」と言えない．記録は，事故のあとで自分たちを守る材料になる．

→ OWASP では A01 アクセス制御の不備，A02 セキュリティ設定の不備，A09 ログとアラートの不備 に当たる．

### 型2: 正しい鍵で入られる（リスト型攻撃）

ファンくる（2026年8月公表）

- 約4日間で 506万回のログイン試行を受け，59389 会員のアカウントに不正ログインされた．
- 氏名，生年月日，郵便番号，電話番号，メールアドレスが閲覧された可能性がある．2アカウントでは不正なポイント交換も確認された．
- 同社はパスワードを復号できない形式（ハッシュ）で保存しており，社内から ID やパスワードが流出した形跡は確認されていない．

つまり，自社のパスワード管理に問題がなくても被害は起きる．攻撃者は他のサービスから漏れた ID とパスワードの組を大量に試し，使い回している利用者のアカウントに「正しい鍵」で入る．成功率は約1%だが，500万回試せば約6万件になる．

防ぐ側が持てる手段は，試行回数の制限，2要素認証，異常なログイン試行の検知である．

→ OWASP では A07 認証の不備に当たる．

### 型3: 自分のコードではなく，使っている部品がやられる（サプライチェーン）

GitHub Actions「tj-actions/changed-files」の侵害（2025年3月）

- 多くのプロジェクトが CI（自動テスト・ビルドの仕組み）で使っていた部品が改ざんされた．
- 改ざん版が実行されると，アクセスキーや各種トークンなどの秘密情報が実行ログに出力された．
- 米 CISA は，該当期間に実行したプロジェクトに対し，秘密情報をすべて漏洩したものとして再発行するよう呼びかけた．

利用側のコードには何の変更もない．バージョン名（タグ）が指す中身が差し替えられたため，いつも通り CI を回しただけで被害を受けた．

現代のアプリは，自分で書いたコードより，取り込んだ部品のほうがはるかに多い．部品の安全性も自分たちの責任範囲である．

→ OWASP では A03 ソフトウェアサプライチェーンの不備に当たる．

### 補足: アプリで防げる範囲，防げない範囲

個人情報保護委員会の令和7年度年次報告によると，漏えい等の報告 17139 件のうち，不正アクセスなど不正な目的によるものは約 22 %である．件数としては誤交付や誤送付といった人為ミスのほうが多い．

この記事が扱うのは，アプリの作り方で防げる部分である．それ以外（誤送信，端末の紛失，フィッシングなど）は運用や組織の領域であり，別の対策が必要になる．

## 2. OWASP Top 10 とは

OWASP（オワスプ）は，Web アプリのセキュリティに取り組む国際的な非営利団体である．OWASP Top 10 は，実際の脆弱性データと専門家への調査をもとに「Web アプリで特に重大なリスク10項目」をまとめたもので，数年ごとに改訂される．最新は 2025 年版である．

対策の抜け漏れを点検するチェックリストとして使える．FanSource でも，この10項目に沿って設計と実装を確認した．

| #   | 項目                                   | ひとことで言うと                     | 建物にたとえると         |
| --- | -------------------------------------- | ------------------------------------ | ------------------------ |
| A01 | アクセス制御の不備                     | 見てはいけない人が見られる           | 部屋ごとの鍵がない       |
| A02 | セキュリティ設定の不備                 | 設定の誤りや初期設定のまま           | 裏口が開けっぱなし       |
| A03 | ソフトウェアサプライチェーンの不備     | 使っている部品に問題がある           | 納品された建材に欠陥     |
| A04 | 暗号化の不備                           | 秘密の守り方が弱い                   | 金庫が簡単に開く         |
| A05 | インジェクション                       | 入力に命令を紛れ込ませる             | 伝票に偽の指示を書き足す |
| A06 | 安全性を欠いた設計                     | 設計の段階で悪用を想定していない     | 図面に非常口がない       |
| A07 | 認証の不備                             | なりすましを防げない                 | 受付の本人確認が甘い     |
| A08 | ソフトウェアまたはデータの完全性の不備 | 途中で改ざんされても気づかない       | 封印のない荷物を受け取る |
| A09 | セキュリティログとアラートの不備       | 攻撃に気づけない，後から追えない     | 防犯カメラも警報もない   |
| A10 | 例外的な状況への不適切な対応           | エラー時に情報が漏れる，守りが外れる | 停電すると鍵が全部開く   |

2021年版からの主な変更点は，サプライチェーン（A03）が部品の脆弱性だけでなくビルドや配布の仕組みまで広げて再定義されたことと，例外時の扱い（A10）が新設されたことである．

1章の3つの型は，それぞれ A01（と A02・A09），A07，A03 に対応する．3章ではこの3項目を詳しく見る．

## 3. 重点3項目: FanSource でやっていること

### A01 アクセス制御の不備

何が起きるか

ログインはできているが，見てよい範囲を超えて他人のデータを見たり変更したりできてしまう状態である．OWASP Top 10 で最も多く見つかる項目である．「画面にボタンを出していない」だけでは防げない．攻撃者は画面を通さず，サーバーに直接リクエストを送る．

FanSource での対策

考え方は「権限の確認を個人の注意力に頼らず，仕組みで強制する」である．

1. サーバーの処理は必ず「認証付きの入口」を通す
   - サーバー側の関数は，認証を確認する共通の入口（ラッパ）経由でしか定義できないようにしている．入口は「未ログイン」「無効化されたユーザー」を拒否する．
   - 入口を通さない書き方は，静的検査（ESLint）がエラーにする．書き忘れた時点で CI が止まる．

2. 「何ができるか」を1か所の表で決める
   - ロール（一般・閲覧専用・管理者）ごとの権限を，1ファイルの表で管理している．

   ```ts
   const ROLE_CAPABILITIES = {
     user: ["writeOwn", "viewResponses"],
     viewer: ["viewAll"],
     admin: [
       "writeOwn",
       "viewResponses",
       "viewAll",
       "writeAll",
       "manageUsers",
       "viewTextAnalysis",
     ],
   };
   ```

   - 各処理は「このユーザーは admin か」ではなく「この操作の権限を持つか」を問い合わせる．ロール名を直接比較するコードも静的検査で禁止している．
   - 権限を見直すときに直す場所が1か所で済み，直し漏れが起きない．

3. 他のクラブのデータは「存在しない」のと同じに見せる
   - 試合や回答へのアクセスは「作成者本人」か「全体閲覧の権限を持つ人」だけに許可している．
   - 権限がない場合と，そもそもデータが存在しない場合で，同じ応答を返す．応答の違いから「その ID のデータは存在する」と推測されるのを防ぐためである．

4. 画面の保護漏れをテストで検知する
   - すべてのページを「ログイン必須」か「公開してよい」のどちらかに分類する一覧を持ち，分類されていないページがあるとテストが失敗する．新しい画面を追加したときの保護漏れを防ぐ．

5. 共有 URL は「知っていれば見える」にしない
   - 外部共有ビューは，推測困難な URL に加えてパスワードを求める．認証後は，署名付きで24時間有効のアクセストークンを発行する．
   - パスワードや URL を再発行すると，発行済みのトークンは即座に無効になる．
   - 1章のコスモ石油の事例（URL を知っていれば見える状態）と同じ形にならないための設計である．

他のプロジェクトで確認したいこと

- 権限チェックはサーバー側で行っているか（画面の出し分けだけになっていないか）．
- 権限チェックを書き忘れたとき，自動で検知できるか．
- ID を別のものに書き換えてリクエストしたら，他人のデータが返ってこないか．

### A07 認証の不備

何が起きるか

本人確認が弱く，なりすましを許す状態である．1章のリスト型攻撃のように，パスワード自体は正しいケースも含む．

FanSource での対策

1. 誰でも登録できる入口を作らない
   - 公開のサインアップ機能を無効にしている．アカウントを作成できるのは管理者だけである．
   - 攻撃者が自分でアカウントを作って内部を探る，という入口をなくしている．

2. 管理者は2段階で本人確認する
   - 管理者は，パスワードの確認後にメールで届く6桁のコードを入力して，初めてログインできる．
   - コードの有効期限は10分である．コードの送信にも回数制限をかけている．
   - 権限が大きいアカウントほど，乗っ取られたときの被害が大きいためである．

3. 試行回数を制限する
   - パスワードは，URL ごとに「5 回まで．以後は 3 分に 1 回だけ回復」としている．総当たりをしても 1 日に試せるのは約 480 回である．
   - 上限に達している間は，正しいパスワードでも照合しない．不一致は監査ログに記録し，短時間に急増した場合は通知する．

4. 無効化したアカウントは即座に締め出す
   - 退職などで無効化したユーザーは，新しいログインを拒否する．ログイン済みのセッションも，次の操作の時点で拒否する．

5. パスワードは自前で扱わない
   - パスワードのハッシュ化と照合は，認証ライブラリ（Convex Auth）に任せている．認証や暗号を自作すると，ほぼ確実にどこかで間違えるためである．

他のプロジェクトで確認したいこと

- ログインやパスワード入力に，試行回数の制限があるか．
- 権限の大きいアカウントに 2 要素認証があるか．
- 退職者や異動者のアカウントを，すぐに止められるか．ログイン済みのセッションも切れるか．

### A03 ソフトウェアサプライチェーンの不備

何が起きるか

利用しているライブラリや CI の部品に脆弱性が見つかる，または悪意あるコードが混入する状態である．自分たちのコードが正しくても被害を受ける．

FanSource での対策

1. 部品のバージョンを「中身」で固定する
   - CI で使う部品は，バージョン名ではなく，中身と1対1で対応する識別子（コミット SHA）で指定している．

   ```yaml
   uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
   ```

   - 1章の tj-actions の事例は，バージョン名が指す中身を差し替える手口だった．SHA で固定していれば，差し替えられたものは実行されない．
   - アプリの依存ライブラリも，ロックファイルに記録された通りのものだけをインストールする（`npm ci`）．

2. 更新を自動で提案させる
   - Dependabot が週次で依存関係の更新を提案する．脆弱性が見つかった場合の対応期限を，重大度ごとに決めている（Critical は24 時間，High は 7 日など）．
   - 固定したままだと古い脆弱性が残り続けるので，「固定」と「定期更新」はセットである．

3. 秘密情報をリポジトリに入れない仕組み
   - プルリクエストごとに，API キーやトークンが混入していないかを自動で検査する（gitleaks）．
   - 検査ツール自体も，ダウンロードしたファイルが想定通りのものかをハッシュ値で検証してから実行する．
   - 検出された場合は，履歴から消すだけで済ませず，その秘密情報を失効・再発行する手順を定めている．

4. CI に余計な権限を与えない
   - CI の権限は「コードの読み取りのみ」に絞っている．CI の部品が侵害されても，できることが限られる．

他のプロジェクトで確認したいこと

- 依存ライブラリの脆弱性を，誰がいつ確認しているか．自動化されているか．
- CI の部品をバージョン名（`@v4` など）で指定していないか．
- 秘密情報がリポジトリに入ったとき，検知できるか．入ってしまった場合の手順があるか．

## 4. 残りの7項目（参考）

共有会では扱わない．関心のある項目を読んでほしい．

### A02 セキュリティ設定の不備

- すべてのページにセキュリティヘッダを付けている．他サイトへの埋め込み禁止，通信の HTTPS 強制，読み込めるスクリプトや通信先の制限（CSP），カメラや位置情報などブラウザ機能の無効化である．
- 共有ビューでは，URL が外部サイトに伝わらないよう，リンク元情報を送らない設定にしている．

### A04 暗号化の不備

- 推測されては困る値（共有 URL のトークン，共有パスワード，管理者の確認コード）は，暗号用の安全な乱数で生成している．
- アクセストークンの署名には標準的な方式（HMAC-SHA256）を使い，署名の比較は処理時間から情報が漏れない方法で行っている．
- ログイン用パスワードは，認証ライブラリがハッシュ化して保存する．
- 共有ビューのパスワードは，管理画面で再表示する仕様のためハッシュ化していない．ランダム生成で使い回しがないこと，試行回数制限があることを前提にした判断で，設計文書に理由を残している．「何を守るためにどこまでやるか」を決めて記録することも対策の一部である．

### A05 インジェクション

- サーバーの関数は，受け取る値の型と形式を必ず検証する．想定外の形の入力は処理に入る前に拒否される．
- CSV 出力では，表計算ソフトが数式として実行してしまう文字（`=` `+` `-` `@` など）で始まる値を無害化している．アンケートの自由記述に数式を仕込まれ，CSV を開いた担当者の PC で実行される攻撃を防ぐためである．
- 画面に HTML を直接埋め込む書き方は使っていない．

### A06 安全性を欠いた設計

- アンケートの回答送信はログイン不要の公開機能なので，大量送信を想定して上限を設けている（試合単位と全体の2段階）．
- 自由記述などの入力長に上限を設け，画面側とサーバー側で同じ値を共有している．
- 回答者を識別する情報を持たないため，上限に達すると正規の回答者も一時的に送信できなくなる．このトレードオフは設計時に認識し，記録している．

### A08 ソフトウェアまたはデータの完全性の不備

- 依存関係はロックファイルの通りにインストールし，CI のキャッシュもロックファイルが完全に一致するときだけ使う．
- CI で整形・静的検査・型検査・テスト・ビルドを実行する．
- 本番への反映は，人間のレビューとマージを経由する運用にしている．

### A09 セキュリティログとアラートの不備

- 管理操作（ユーザーの作成や権限変更，試合の削除，共有設定の変更など）を監査ログに記録している．ログには個人情報や秘密情報を含めず，365 日で自動削除する．
- 重要な操作（ユーザー作成，権限変更など）はメールで通知する．
- 権限エラーやレート制限の発生を構造化ログに出力し，外部の監視サービスで急増を検知する構成にしている．
- エラー監視サービスには，個人情報を取り除いてから送信する．
- 個人データの漏えいを想定したインシデント対応手順書を用意している．初動の判断，報告期限，封じ込めの手段，通知文のテンプレートを含む．

### A10 例外的な状況への不適切な対応

- エラー画面には「問題が発生しました」と再試行ボタンだけを表示し，内部の情報は出さない．
- 利用者に見せるエラーメッセージは，あらかじめ決めた文言だけにしている．
- メンテナンスモードを用意し，問題発生時にサービス全体を安全側に止められる．
- 通信が切れたときは，原因の見当がつく案内を表示する．

## 5. まだできていないこと

対策に終わりはない．現時点で認識している課題を，分類のレベルで挙げる．

- 認証: 2要素認証は管理者のみである．一般ユーザーのパスワード要件は，ライブラリの標準（8文字以上）のままである．
- サプライチェーン: コードの脆弱性を自動で探す静的解析（SAST）は導入していない．依存関係の脆弱性は Dependabot の通知で把握している．
- 入力検証: 受け取る値を検証するルールは，規約とレビューで守っている．自動検査による強制はできていない．
- デプロイ: CI の成功を必須にするブランチ保護は，契約プランの制約で使えず，人間のレビューで補っている．

大切なのは，できていないことを把握し，優先順位を付けておくことである．

## 6. チェックリスト

### 開発する人向け

1. 権限チェックはサーバー側にあり，書き忘れを自動で検知できるか．
2. ログインやパスワード入力に試行回数の制限があるか．
3. 依存ライブラリと CI の部品を固定し，定期的に更新しているか．
4. 秘密情報（API キーなど）がリポジトリに入っていないか．入ったら検知できるか．
5. 「誰が，いつ，何をしたか」を後から追えるログがあるか．

### 開発を依頼・レビューする人向け

- 「このデータは，誰が見られる設計ですか．それをどこで確認していますか」
- 「使っているライブラリに脆弱性が見つかったら，誰がいつ気づきますか」
- 「もし漏えいが起きたら，最初の1時間に何をしますか」
